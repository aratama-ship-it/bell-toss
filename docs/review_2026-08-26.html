土台は健全です。物理モデル（両鳴り・回復時間・脇の左右）と検証ツール3種は実測に基づいて作られており、振付そのものの品質は高い。問題は「完成曲を守る仕組み」に穴が2つあることと、スケジューラーが巨大な1関数に育ってしまい、変更のたびに実測で確かめるしかないことです。UI/UXは方向が固まっており、次は「いま自分が何を見ているか（完成版か、編集中か）」を常時見せることが最優先です。

内部レビュー（重大度順）

重大 #1 自動保存からの復元で、完成曲の焼き付けが効かない

js/main.js applySongData（復元経路）／init() 1830行付近／freezeSeed は loadPreset 1582行でしか呼ばれない
事実（再現済み）: ?song=bunbun で開く → 400ms後に自動保存 → URLのパラメータなしで開き直す → 復元経路は applySongData を通り、焼き付けも確定seedも適用されないまま200シード探索が走る。結果: パス82%→76%、開始時の構えが「右手ミ／左手ソ」→「左手ソ／右脇ミ」に変化。セレクタは「ぶんぶんぶん」のまま、通知も出ない（楽譜は同一なので「編集済み」判定にならず、通知文自体が出ない）。

影響: 「完成曲は1ミリも動かない」という保証が、ブックマークやリロードという最も普通の操作で破れます。クライアントが焼き付け版と違う振付を稽古する事故につながります。

修正案（小）: 復元時に「保存データが元のプリセットと同一」なら loadPreset(saved.id) に流す（焼き付け・seed・UIの初期化が全部そちらにある）。差分があるときだけ applySongData。加えて applySongData の末尾で「元のプリセットに一致すれば freezeSeed を適用」を入れると二重に安全。

重大 #2 探索の早期打ち切りが「ロック破り」を見ていない

js/scheduler.js TOREI.schedule 258〜260行
事実: 打ち切り条件は fails===0 && shakes===0 && chordMiss===0 && openPass && passRate≥0.6。fixDrops（人間の指定・ロックを守れなかった回数）が含まれていない。採点では×50で強く罰しているが、打ち切りはそれより前に起きる。

影響: ロックを破ったシードが上の条件を満たすと、そこで探索が止まり、より良い（ロックを守る）シードに到達しない。今日の実測でロックが守られたのは、最初の候補が偶然ロックを守っていたため。ロックの信頼性が運に依存している状態です。

修正案（1行）: 打ち切り条件に && (m.fixDrops||0)===0 を追加。加えて、人間の指定が1つでもある曲では早期打ち切りを無効化して200シード全部回す（編集中の数百msは許容範囲）と、ロックの安定性がさらに上がる。

高 #3 焼き付けデータに「どの楽譜のものか」の証明がない

js/frozen.js／tools/freeze.mjs／js/main.js freezeSeed
事実: frozen.js は seed・日付・行動列を持つが、対応する楽譜（音符・BPM・設定）のハッシュを持たない。songs.js を再生成して1音でも変われば、焼き付けは黙って別の楽譜に貼り付く。
修正案: 焼き付け時に楽譜＋設定の署名（stateSig と同じ形）を保存し、読み込み時に照合。不一致なら「焼き付けが古い」と通知して探索に落とす。検証ツールにも同じ照合を入れる。

高 #4 検証が「人が3つのツールを覚えて回す」前提で、自動化されていない

tools/analyze.mjs・invariants.mjs・check_held_catch.mjs／package.json なし／CI なし
事実: 今日一日で私はこの3本を十数回手で回した。忘れれば壊れたまま公開できる（実際、fixDrops の見落とし #2 はツールでは検出できない種類の穴）。
修正案: tools/verify.mjs 1本に統合し、①3種の検査、②焼き付けの署名照合、③完成曲のハッシュ固定（bunbun=2db3c6b6…）を回して、1つでも落ちたら非0で終了。デプロイ前に必ず実行する運用に。将来 GitHub Actions に載せれば push 時に自動化できる。

中 #5 スケジューラーの巨大関数

js/scheduler.js _scheduleOnce（265〜1480行、約1,200行の単一クロージャ）／planToss 274行／scheduleNoteIndependently 250行

解釈: 物理ルールが増えるたびに planToss の中に条件が足されてきた（脇の左右・抜いてから渡す2段・見せ場・ロック…）。単体テストが書けず、「変更→全曲実測」でしか安全を確かめられない。今日のようにルール追加が続く限り、回帰のリスクは増える一方。

修正案（段階的）: まず planToss を「取得計画（脇/スタンド/手）」「投げ窓の判定」「受け手の選定」「コスト計算」の4つに切る。次に _scheduleOnce の状態（perfs・rings・airborne・warnings）をオブジェクトに束ね、各関数がそれを受け取る形へ。振る舞いは変えず、全曲ハッシュ照合で同一性を確認しながら進める。

中 #6 採点の重みが散在している

js/scheduler.js scoreResult（1000／50／10／2／3／8／6／100／0.6／1.0／0.5／0.4…）と TOREI.EFFORT、計画時コスト（WAKI_ARM_COST ほか SCHED 定数）

解釈: 一部は EFFORT に集約されUIから触れるが、パスの頭打ち（0.70/0.80）や冒頭パス（1.0）などはコードに直書き。「どの重みが何を動かすか」の一覧がなく、次に重みを足すときに衝突（例: 高さを揃える vs バリエーション）を見落としやすい。

修正案: 重みを1つの表 TOREI.WEIGHTS（名前・既定値・単位・由来日）にまとめ、scoreResult はそれだけを参照。UIの「無理のなさ」パネルもこの表から生成する。

中 #7 キーボード操作が二系統で、衝突する

js/main.js 編集卓の keydown（capture, ←→=前後の投げ・1〜5=高さ）と onKey（←→=再生位置の16分移動・Shift+←→=小節）

事実: 投げを選択している間は ←→ が「前後の投げ」に奪われ、再生位置の移動ができない（Escで解除すれば戻る）。設計上は妥当だが、画面にそのルールが出ていないので「矢印が効かない」と感じる場面が出る。

修正案: ルールを一本化して画面に明記（「投げを選択中は ←→ で投げを移動、Esc で解除」は編集卓の空欄に既に書いてある。選択中の編集卓にも同じ一行を出す）。

中 #8 自動保存が「曲IDごと」ではない

js/songfile.js キー torei.work 1つ／曲を切り替えると上書き

解釈: 作曲者1人の作業には十分だが、クライアントが「第九を組み直し→ぶんぶんぶんを確認→第九に戻る」と操作した瞬間に第九の編集が消える（通知は出るが、消える事実は変わらない）。

修正案: キーを torei.work.<曲id> にして曲ごとに保持。加えて「この曲の編集を破棄して完成版へ戻す」ボタンを明示的に置く。

低 #9 細かな整理

  • js/presets_backup_2026-08-22.js: どこからも読まれていない。iCloud同期の対象にもなるので、archives へ移すか削除（削除は本人承認フローで）。
  • js/audio.js だけ ?v= が無い（index.html 265行）。次に音源を変えたときキャッシュで更新が届かない。
  • js/timeline.js: 死んだ変数 yo = 0、catchLaneY の - 0 * BAND_H。動作に害はないが読み手を迷わせる。
  • tools/optimize.mjs のヘッダ説明が「既定2000シード」のままだが、実運用は 8000。文書と実態を揃える。
  • MIDI取り込み（main.js parseMidi）: SMPTE非対応は明示エラーになっている（良い）。未確認: 拍子メタ（0x58）を読んで beatsPerBar に反映しているか。反映していなければ 3/4 の曲を読むと 4/4 として並ぶ。

良い点（維持すべきもの）

  • 物理モデルの決め方が一貫して「本人の実演知識 → 実測で重みを決める」になっている（両鳴り・回復時間・脇の左右・見せ場の重み3.0など）。根拠がPROJECT_NOTESに残っている。
  • 完成曲を「振付データそのもの」で焼き付ける判断は正しい（seed固定では守れないことを実証した上での設計）。#1・#3 を塞げば堅い。
  • 検証ツールが3軸（音楽・物理・不変条件）で分かれており、何が壊れたかが分かる。
  • 音の同期（出力遅延の補正、ループ境界の算術連結）は堅実。Safariの非対応も手動補正で逃がしている。

UI/UX レビュー

前提: 使うのは音楽の演出家（非エンジニア）。場面は「最適化された振付を見て、譲れない箇所を固め、残りを組み直す」。設計方針（第一案の固有性・中心体験の深さ）に照らして見ています。

最優先 E. 「いま見ているものは何か」が画面に出ていない

事実: 完成版（焼き付け）・確定seed・編集中・探索中の4状態があるのに、画面上の手がかりは金の四角と🔒だけ。#1 のバグが人の目に見えなかったのはこのため。

提案: 曲名の横に状態バッジを常時表示。「完成版（凍結・2026-08-26）」「編集中（完成版から離れています ／ 戻す）」「おまかせ（探索結果）」。編集で自動的に切り替わり、「戻す」で完成版へ復帰。これは機能というより信頼の表示で、クライアントに渡す前に必ず要る。

高 A. 上部の設定群がクライアントにはノイズ

事実: 演者数・滞空・脇の本数・スタンド持ち替え・パッシング・リング上限・振り・音ズレ補正＋「無理のなさ」6項目が、舞台のすぐ下に常時並ぶ。これらは作曲者（あなた）の道具で、演出家が触るものではない。

提案: 画面を2つの役割に分ける。既定は「見る・組み直す」画面（舞台／再生／ダイヤグラム／編集卓／Qシート）。設定群は「作曲者の設定」として1つの折りたたみに収め、開いたときだけ出す。共有リンクに ?mode=client を付けたら設定を隠す、でも良い。

高 B. 編集卓の「波及」表示が消えてしまう

事実: 「後続◯投も変わった」は2.6秒で光が消え、状態行の文も次の操作で上書きされる。演出家が「何が変わったか」を後から辿れない。

提案: 編集卓に小さな「変更の履歴」（最新5件: 何を→どうした→何投に波及、クリックで該当箇所へ）。「元に戻す」も1段から履歴ベースの多段へ。DAWで言うアンドゥ履歴パネル。

中 C. ダイヤグラムの色: 複製リング（ミ①・ミ②）が同色

事実: 色は音高で決まるので、複製2本は帯のラベルでしか区別できない。帯が細い区間では追えない。

提案: ②以降を斜線（ハッチ）や点線の縁で描き分ける。色数は増やさない（音高=色の対応を崩さない）。

中 D. iPadでの操作が想定されていない部分

事実: ループ範囲は option+ドラッグ（PC前提）。44pxのタッチ対応は入っているが、option キーはない。楽譜の音符移動もドラッグ前提。

提案: ループは「この小節を反復」＋「反復範囲を広げる/狭める」ボタンで代替できると明記。iPadは 未検証なので、クライアントが iPad を使うなら一度実機で通しで確認する。

中 F. 言葉の混在

  • 「パッシング: 多め／natural／off」— 選択肢が英語混じり。「多め／必要なときだけ／なし」に。
  • 「同音リング最大」「リング上限」「脇に挟める数」— 単位の「本」が付くものと付かないものがある。揃える。
  • 編集卓の「おまかせ」「受ける人」「受ける手」「投げの高さ」は良い。同じ語彙を設定群にも波及させる（例: 「振り」→「手元で振って鳴らす」は既に良い）。

低 G. その他

  • Qシートと編集卓の連動: 編集卓で投げを選んだら、Qシートの該当行も強調すると「紙で見る手順」と「図」がつながる。
  • 舞台の名札の下線は薄すぎて「押せる」と気づきにくい。ホバーで濃くする程度でよい。
  • アクセシビリティ: canvas主体で読み上げは対象外と割り切っている（妥当）。focus-visible・44px は入っている。色のみの区別は帯ラベルで補われている。
